# Тренировочный движок JogJoy: что переносить в Android-приложение «здоровье»

Источник: репозиторий antontikhomirov/jogjoy_app, коммит da99e8c (2026-11-18). Только чтение, ничего не менялось.

## Стек JogJoy
- Клиент: Expo SDK 58 / React Native 0.88, TypeScript, Expo Router. Состояние приложения целиком в одном объекте `AppState` (AsyncStorage, бэкап на сервер).
- Здоровье: react-native-health-connect (Android), HealthKit (iOS).
- Сервер: Python (`server/app.py`), PostgreSQL для RU-сервера, анализ техники по видео, чат-коуч на Claude.
- **Генерация плана и адаптация полностью детерминированные, без LLM.** Это чистые функции на TS в `src/engine/` (~2300 строк + 22 теста). LLM используется только в чате-коуче (`server/jogjoy_chat.py`), и ему прямо запрещено менять план.

## Ключевые файлы
| Файл | Что внутри |
|---|---|
| `src/engine/types.ts` | Модели: Profile, Baseline, GoalInput, Plan → PlanWeek → Workout → WorkoutStep, Paces, WorkoutLog, AdaptationProposal. Методика «training-load policy v0.3». |
| `src/engine/levels.ts` | Уровень бегуна (beginner/base/intermediate/advanced) по объёму, частоте, длительной; при расхождении берётся нижний. |
| `src/engine/paces.ts` | Прогноз Ригеля (k=1.06, +7.5% для марафона при <50 км/нед) и темпы по VDOT Дэниелса. |
| `src/engine/rules.ts` | Все числовые правила: длина плана по дистанции, пиковые объёмы, +10%/нед и +20%/2 нед, разгрузка каждые 3–4 недели, доли Z1 ≥75% и Z4–5 ≤10%, кэп одиночной пробежки (+10% к самой длинной за 30 дней), тейпер. |
| `src/engine/templates.ts` | Шаблоны тренировок (easy, long, tempo, fartlek, hills, интервалы, run-walk, контрольный забег), кэпы качественной работы от недельного объёма, ротация ключевых по фазам. |
| `src/engine/generate.ts` | Генератор: фазы base/build/specific/taper (или maintain для цели «здоровье», run-walk для новичков), выбор дней, разгрузки, ключевые сессии. После сборки план прогоняется через валидатор и при нарушении неделя урезается и пересобирается (до 80 попыток). |
| `src/engine/validate.ts` | ~20 проверок плана (weekly_increase, z1_share, hard_days_adjacent, single_run_cap, taper_volume…). |
| `src/engine/adapt.ts` | Адаптация плана по логам: пропуски, RPE, боль, болезнь. |
| `src/engine/move.ts` | «Сделать пропущенную сегодня»: перенос в пределах недели. |
| `src/lib/useAdaptation.ts` | Когда вызывать адаптацию: при каждом изменении логов и раз в день; помнит отклонённые предложения. |
| `src/lib/healthImport.ts` | Импорт пробежек из Health Connect: сопоставление с планом, partial при <60% дистанции, остальное в «лишние пробежки». |
| `src/lib/hr.ts` | Пульсовые зоны Z1–Z5: Карвонен при известном пульсе покоя, иначе % от макс. |
| `src/app/workout/done.tsx` | Экран лога: статус, RPE 1–10 (обязателен, если бежал), боль 0–10, болезнь. |

## Лог тренировки
`WorkoutLog { workoutId, date, status: done|partial|skipped, rpe (CR-10 Фостера), pain 0–10, painLocation, painRedSigns, illness: none|above_neck|systemic|cardiac, actualKm, durationSec, note, source: 'health'? }`

## Алгоритм адаптации (`proposeAdaptation(plan, logs, today)`)
Работает над копией будущих тренировок и возвращает **предложение** (было/стало по каждой тренировке и объём недели до/после). Пользователь принимает или отклоняет; только красные флаги ставят план на паузу сразу. У предложения детерминированный id, поэтому повторно оно не всплывает.

1. **Красные флаги** (последний лог не старше 3 дней): сердечные симптомы или боль ≥5 или «тревожные признаки» → пауза плана, к врачу.
2. **Пропуски** (разрыв с последней пробежкой):
   - одна пропущенная длительная → переносится на ближайшую лёгкую этой недели, если перед ней нет ключевой;
   - 2–4 дня → ближайшая ключевая становится лёгкой;
   - 5–10 дней → ключевые на 7 дней в лёгкие, объём недели до уровня последней разгрузочной (или 75% текущей);
   - 11–28 дней → ключевые на 14 дней в лёгкие, неделя 1 = 60%, неделя 2 = 70% от объёма до перерыва;
   - больше 28 дней → нужен новый план (новая анкета).
3. **Усталость по RPE:**
   - две лёгкие/длительные за 7 дней с RPE ≥7 → следующая неделя: первая ключевая ×0.7, остальные ключевые в лёгкие, лёгкие ×0.75, длительная ×0.7 (кроме разгрузки и тейпера);
   - последняя ключевая не выполнена (partial) или RPE 10 → следующая ключевая на ступень легче (минус повтор или +5 с/км);
   - две ключевые подряд на 2+ балла легче ожидаемого RPE (Z4–5 ≈ 8.5, Z3 ≈ 6.5, Z2 ≈ 5) → вместо следующей ключевой контрольный забег 3–5 км для пересчёта зон.
4. **Боль 3–4** (или любая боль две тренировки подряд) → ключевые на 7 дней в лёгкие, длительная ×0.7.
5. **Болезнь:** «выше шеи» → ключевые на неделю в лёгкие; системная → 2 дня отдыха + ключевые в лёгкие.

## Рекомендация по переносу
**Портировать `src/engine/` вручную в Kotlin как чистый модуль без Android-зависимостей.** Не встраивать JS-движок (QuickJS/J2V8) и не заменять движок LLM: правила точные, проверены тестами и дешёвые.

- Модели: `data class` + `enum`/`sealed interface` (GenerationOutcome, AdaptationReason). Даты как `LocalDate` (java.time) вместо ISO-строк.
- Функции один в один: levels → paces → rules → templates → validate → generate → adapt → move. Убрать `process.env` и глобальную переменную `UNCHECKED` из generate.ts.
- Тесты: прогнать TS-движок на 20–30 профилях, выгрузить планы и предложения адаптации в JSON и использовать как эталон в JUnit для Kotlin-версии.
- Room: таблица `workout_log` (одна строка на лог), таблица `plan` с планом в JSON-колонке (kotlinx.serialization), `adaptation_decision` (принято/отклонено). Так проще, чем нормализовать недели/тренировки, и совпадает с логикой JogJoy.
- Health Connect: `ExerciseSessionRecord` (running, treadmill) + `DistanceRecord` → логика `healthImport.ts` переносится без изменений.
- Claude: только для объяснения предложений адаптации и чата, по образцу `SYSTEM_PROMPT` из `server/jogjoy_chat.py` (без диагнозов, не говорить, что план изменён).

Оценка объёма: ~2–2.5 тыс. строк Kotlin, 2–4 дня с Claude Code, включая эталонные тесты.

## Ограничения
- Движок только для бега. Силовые, велосипед и т.п. он не планирует; если они нужны в модуле тренировок, это отдельная логика (можно переиспользовать каркас адаптации: RPE, пропуски, боль).
- Для личной цели «вес/здоровье» достаточно режима `health` (фаза maintain) и адаптации; гоночная часть (тейпер, VDOT, марафонские правила) может подождать.
- Методика в коде помечена как утверждённая версия v0.3 от 2026-10-17. В репо нет внешнего обоснования порогов, так что это правила JogJoy, а не проверенные мной научные нормы.
